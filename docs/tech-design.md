# 智能 OnCall Agent — 技术设计

一个值班辅助系统：告警发进 Slack，工程师 @ 一句话，它读得到 thread 里的告警和讨论，
自动规划排查步骤、调工具取证、给出诊断报告。也可以直接和它对话，问服务是干什么的、
某个错误码什么意思。

三块能力：**知识库**（文档向量化，团队经验沉淀）、**对话**（自然语言查手册）、
**运维诊断**（Plan-Execute-Replan 自动排障）。

技术栈：FastAPI + LangChain/LangGraph + Milvus + MCP + Slack Socket Mode。

---

## 1. 定位

目标是**把值班前十分钟里那些机械的取证工作自动化**，不是取代工程师判断。

一次告警响应大致是：定时间窗 → 看监控定服务 → 查日志找线索 → 关联最近变更 → 判断
是故障源头还是下游受害者 → 量化影响。其中前几步是纯粹的数据聚合，每次都一样，
但每次都要人手动敲。

所以输出分成两半：

```
┌─ 证据（工具查回来的事实） ──────────────────────────┐
│  时间窗、监控指标、日志片段、告警清单                │
│  每一条都带着它是哪个工具、什么查询查回来的          │
└─────────────────────────────────────────────────────┘
┌─ 判断（模型的分析） ────────────────────────────────┐
│  根因假设、故障源头 vs 受害者、下一步建议            │
│  每个结论要指出它依据的是上面哪条证据                │
└─────────────────────────────────────────────────────┘
```

**证据那半必须正确或缺失，不能猜。** 判断那半允许错，但要说清楚依据。

事故当中，一个自信的错答案比没有答案更糟——它会把人带向错误方向，而当时最缺的就是时间。

## 2. 三个 Agent 和它们的编排

### 2.1 各自是什么

| Agent | 形态 | 干什么 |
|---|---|---|
| **知识库 Agent** | 上传 → 切分 → 向量化 → 建索引 | 把故障手册、接入文档灌进 Milvus |
| **对话 Agent** | `create_agent`（tool-calling + 会话记忆） | 自然语言问答，一到两轮工具调用 |
| **运维 Agent** | LangGraph `StateGraph`（Plan-Execute-Replan） | 收到告警自动规划步骤、调工具、出报告 |

知识库 Agent **不参与运行时编排**——它是写入管道，由文件上传或 `make upload` 触发，
不是 @ 出来的。真正需要编排的只有对话和运维两个。

### 2.2 网站有导航栏，Slack 没有

这是编排设计的起点。

Web UI 可以把三个功能做成三个入口，因为用户自己会点。Slack 里用户只会 @ 一句话——所以
**Slack 强制在入口处统一**。

但"入口统一"不等于"执行统一"。一个知识问题（"错误码 43 什么意思"）不需要 Plan-Execute-Replan
跑四次模型调用；一次告警排查也不该退化成一问一答。**两种形状都要保留，由路由决定走哪个。**

### 2.3 路由：事实归代码，意图归模型

```
@oncall-agent
   │
① 这个 thread 里有告警吗？          代码，读 Slack 元数据
   │                                （root 消息的 bot_id / app_id / 频道配置）
   ├── 没有 ──────────────────────► 对话 Agent
   │
   └── 有 ──► ② 这句话是要排查它，还是在问别的？    小模型，仅当①为真时才调用
                ├── 想排查 ────────► 运维 Agent
                ├── 拿不准 ────────► 运维 Agent
                └── 只是提问 ──────► 对话 Agent + 声明没有排查，一句话可升级
```

**①是事实，不该问模型。** Slack 已经知道 root 消息是谁发的。问模型"这是不是告警"，
它可能看错；查 `bot_id` 不会。

而且这一条读的是**来源**不是**内容**——所以**一条从没被登记过的告警照样能触发完整排查**。
关键词表（`app/slack/alerts.py`，从 `aiops-docs` 里的 `**告警名**:` 自动提取）是最后一条规则，
只服务"工程师手动把告警文本粘进来"这一种情况。

**②是真判断，没有结构性替代。** "是不是又是冷启动？"和"data-sync-service 是干嘛的？"都是打在告警
thread 里的问题，只有语义能分开。

### 2.4 让②安全的三件事

一个语义闸门有静默判错的风险，所以：

**偏向写死在代码里。** 两种误判代价不对称——把提问当排查，浪费一分钟；把排查当提问，
工程师会**以为**已经排查过了。所以分类器异常、判决无法解析、空 @ 一律返回 `investigate`
（`app/slack/intent.py`）。

**判错必须可见。** 告警 thread 里走了对话，回复末尾加一句：

> _我把这句理解成提问而不是排查请求，所以没有查这条告警。说一声 investigate 我就去查。_

误判本身不可怕，**静默的误判**才可怕。一句话能纠正的判错是麻烦，看不见的判错才是问题。

**判断留在执行层外面。** 路由在 `app/slack/router.py` 决定，两个 service 都不参与。
"这次不用排查"这个结论一旦能由执行层自己下，就没人看得见它下错了。

### 2.5 窄问题不等于窄排查

有一条容易踩反的：**"是不是又是冷启动？"要归到 `investigate`。**

它确实是在问这条告警，只是框得很窄。如果因为这句话就只查冷启动，那正好错过了真正的原因——
提问的人本来就是在猜。**问题可以改变回答的重点，不该缩小取证的范围。**

## 3. 运维 Agent：Plan-Execute-Replan

### 3.1 为什么不是单纯的 ReAct

排障是多步的，而且**中途会发现方向错了**。ReAct 每轮只能选下一个工具，没法说"我这个思路
不对，重新规划"。Plan-Execute-Replan 有这个能力。

```
用户任务（告警文本 + 工程师的问题）
   ▼
Planner    先检索知识库拿相关经验 → 结合可用工具清单生成分步计划
   ▼
Executor   取计划第一步，选工具，执行，结果追加进 past_steps
   ▼
Replanner  三选一：continue │ replan │ respond
   │              │           │
   └──────────────┘           ▼
      回 Executor          最终报告
```

图定义在 `app/services/aiops_service.py`，节点在 `app/agent/aiops/`。
`MemorySaver` + `thread_id` 做会话持久化。

### 3.2 Planner 先查知识库，不是事后参考

这是个位置选择，值得说明。

RAG 检索发生在**制定计划之前**，检索到的手册作为"相关经验"进 planner 的 prompt。所以那 5 篇
`aiops-docs` 实际上是**计划模板**——它们的"排查步骤"章节直接写了该调哪个工具、传什么参数：

```markdown
### 步骤2: 查询系统日志
**工具**: `query_logs`
**参数要求**: 地域 ap-guangzhou / 日志主题 system-metrics / 时间范围 最近30分钟
```

放在最后当参考，模型只能拿它验证结论；放在最前面，它能直接决定查什么。**团队经验因此变成
可执行的东西，而不是读物。**

### 3.3 循环终止靠代码，不靠提示词

Replanner 的 prompt 里写了一堆"优先 respond""已执行 >= 5 禁止 replan"。**那些是建议。**
真正生效的是这几条：

| 守卫 | 位置 | 作用 |
|---|---|---|
| `MAX_STEPS = 8` | `replanner.py:130` | 硬上限，先于模型判断 |
| `new_steps[:len(plan)]` | `replanner.py:213` | 重规划只能缩短不能增长——"再加三步"不可表达 |
| `len(past_steps) >= 5` 禁止 replan | `replanner.py:216` | 防止反复重规划耗尽预算 |
| 未知 action 落到 continue | `replanner.py` else 分支 | 模型返回意外值不会卡死 |

值班场景下，一个查得很全但在故障结束后才出来的答案没有价值。**预算必须是代码里的分支，
不是提示词里的请求。**

### 3.4 工具

本地三个 + MCP 两组：

| 工具 | 来源 | 说明 |
|---|---|---|
| `retrieve_knowledge` | 本地 | Milvus 向量检索 |
| `get_current_time` | 本地 | 确定时间窗 |
| `query_prometheus_alerts` | 本地 | **真打** `/api/v1/alerts` |
| `query_cpu_metrics` / `query_memory_metrics` | MCP `monitor` | 监控数据 |
| `search_log` / `search_topic_by_service_name` 等 | MCP `cls` | 日志查询 |

MCP 走 `MultiServerMCPClient`，带重试拦截器（指数退避 ×3）和 `load_tools_safe`——MCP 服务
挂掉时降级成空工具列表并给出可读错误，而不是让整个排查崩掉。

**当前 monitor 和 cls 两个 MCP server 返回的是算法生成的模拟数据**（`random.uniform()` 加
斜坡），只有 Prometheus 告警查询是真的。接真实后端时替换这两个 server 即可，agent 侧不用改。

## 4. 对话 Agent

`create_agent`（LangGraph 原生 tool-calling）+ `MemorySaver`，`session_id` 作 `thread_id`。
共用运维 Agent 的同一套工具。

`trim_messages_middleware` 控制上下文长度——一条 thread 聊一下午不能让 prompt 无限增长。

SSE 流式输出（`app/api/chat.py`）解决大模型响应延迟的体感问题：先出字，而不是转圈 20 秒。

## 5. Slack 接入

### 5.1 两个进程

`oncall-slackd` 持有 Socket Mode 长连接，`oncall-api` 提供 HTTP/SSE 和 Web UI。
**两个进程，不是一个。**

bolt-python 的维护者明确不建议 web app 和 WebSocket 客户端共用一个 event loop；社区常见的
FastAPI lifespan 变通方案在 `uvicorn --workers > 1` 下直接坏掉——每个 worker 开一条自己的
WebSocket，每个 Slack 事件被处理 N 次。

拆开还顺带带来重启独立性：部署 API 不会断掉 Slack 连接。

Socket Mode 是往外拨的，不需要公网入口。这在这里是必需而非偏好——agent 的工具要连 Milvus、
MCP server 和内网监控，进程本来就得待在网内。

### 5.2 3 秒 ack，然后后台跑

Socket Mode 和 Events API 一样有 3 秒死线：必须在 3 秒内把 envelope ack 回去，否则 Slack 重投。
而一次排查要 60–120 秒。

```python
@app.event("app_mention")
async def on_mention(event, ack, client):
    await ack()                                    # 永远先 ack
    asyncio.create_task(run_slack_turn(...))       # 真正的活丢后台
```

ack 之前不碰 Milvus、不碰 MCP、不碰模型。

另外：**handler 里的异常必须捕获并报进 thread**。Slack 的规则是一小时内投递失败率超过 95%
会**停用整个 app 的事件订阅**，需要手动去后台重新启用——一个崩溃重启循环的容器能把 bot 直接
搞下线。

### 5.3 进度要发，但要合并

一个事故频道盯着 bot 沉默 90 秒，会认为它挂了。但 `chat.update` 是 Tier 3，Slack 建议每频道
约每秒一次。

`app/slack/progress.py` 做合并写入：第一条立刻发（工程师需要看到它开始了），之后最快 1.5 秒
一次，最后一条无条件发，遇到 429 按 `Retry-After` 拉长间隔而不是丢更新。

Slack 较新的 `chat.startStream`/`appendStream` 配额更高（Tier 4）且接受真 Markdown，实现在
`slack_use_streaming` 开关后面，**默认关**——官方文档说 thread 范围的 streaming 会返回
`invalid_thread_ts`，但 SDK 自己的示例又在传 `thread_ts`，两者矛盾，而值班 bot 就活在 thread 里。
代码在这个错误上回退到 `chat.update`，所以打开开关去真实 workspace 里试是安全的。

### 5.4 读 thread，不读频道

| API | 范围 | 用不用 |
|---|---|---|
| `conversations.replies(channel, ts)` | 单条 thread | ✅ 默认路径，上限 50 条 |
| `conversations.history(channel)` | 整个频道 | ❌ 不在默认路径上 |

事故频道很吵。同时可能有五条无关告警，全拉进来只会稀释证据、制造"到底在问哪条"的歧义。

消息分类（路由依赖这个）：

| 发送方 | 特征 |
|---|---|
| Incoming Webhook 告警 | `subtype="bot_message"`，有 `bot_id`，**没有 `user`** |
| Bot token 告警 | 有 `bot_id` + `app_id`，无 `bot_message` subtype |
| 人类 | 有 `user`，无 `bot_id` |
| 我们自己 | `bot_id` 等于自己的 |

**`bot_id` 和 `bot_user_id` 是两个不同的 ID**（`B...` vs `U...`）。流传很广的一个参考实现拿
这两个互相比较，所以它那段"跳过自己消息"的逻辑其实从未生效。这里两个都在启动时从 `auth.test`
解析并分开存。

### 5.5 顶层 @ 和 thread 内 @

`thread_ts` 只在 thread 内的回复上才有。常见写法 `event.get("thread_ts") or event["ts"]` 用来
**寻址**是对的，但它会把"频道里的顶层 @"伪装成"一条只有自己的 thread"——而这正是路由要区分的。
`in_thread(event)` 显式报告这件事。

顶层 @ = 没有告警上下文 = 对话。两个例外：

- **告警文本直接贴在 @ 里** → 按告警名或 `[FIRING]` 标记识别，走排查，不需要读历史
- **顶层 @ 且像在指涉刚才那条告警**（配置过的告警频道内）→ 给一个**提议**：
  "这个频道 5 分钟前有条 HighCPUUsage，是这条吗？"——是提议，不是假设

### 5.6 一次 @ 一次排查

Slack 会重投未 ack 的事件，重连时也会重投；跑多个 slackd 副本时重复投递是常态。没有幂等键的话，
一次 @ 会变成两次排查、两条回复。

`event_id` 做幂等键（`app/slack/dedupe.py`）。**认领要在这一轮被持久记录之后进行**——反过来先
认领再排队的话，进程一重启，认领记录还在，而那条本该重试的投递被它挡住了，等于永久丢失。

### 5.7 mrkdwn 不是 Markdown

`**粗体**` → `*粗体*`、`[文字](链接)` → `<链接|文字>`、`-`/`*` 列表 → `•`、标题去掉 `#` 转粗体。
模型输出的 Markdown 直接发进 Slack 会渲染错。

## 6. 知识库

Milvus 向量库，`aiops-docs/` 下的 markdown 是初始语料。

**切分和 TopK 是一组权衡，不是拍脑袋的常数：**

- 分块太小 → 上下文断裂，检索到的片段说不清一件事
- 分块太大 → 一个块里混了多个主题，相似度被稀释，精度下降
- TopK 太大 → 无关内容挤进 prompt，还增加延迟
- TopK 太小 → 漏掉关键信息

当前配置 `chunk_max_size=800` / `chunk_overlap=100` / `rag_top_k=3`。
文档切分用两级策略（`document_splitter_service.py`）：先按结构切，再用递归字符分割器
以两倍 chunk_size 做二次切分，减少碎片。

## 7. 工程上的几个决定

### 7.1 import 期不做 I/O

原实现有两个模块级单例在 import 时就动手：构造 embedding 客户端（没 key 就抛）、连接 Milvus
（没起来就抛）。

后果是**整个进程连 import 都过不去**——包括根本不做检索的 Slack bot 和测试。现在两者都改成
延迟构造，失败推迟到真正要用的那一刻，报错也指得更准。

一个模块被 import 不代表它会被用到。构造函数里连数据库，等于让所有 import 它的人都为一个
可能用不上的依赖付费。

### 7.2 降级而不是崩溃

- MCP 服务不可达 → 空工具列表 + 可读错误，排查继续（能力变弱，但不是全挂）
- 知识库检索失败 → planner 拿不到经验，照样能基于工具清单制定计划
- Milvus 没起来 → 对话和排查都能跑，只是没有 RAG

**但模型不可用是错误，不是降级模式。** 一份静默少了一半分析的回复，渲染出来和完整的一模一样，
事故当中没人会停下来核对。宁可明确说"我现在答不了"。

### 7.3 一个入口，一套记忆

Slack thread 的 `thread_id` 是 `slack:{team}:{channel}:{thread_ts}`，直接作为两个 service 的
`session_id`。所以同一条 thread 里的追问天然带上下文，不需要额外的记忆层。

## 8. 目前的边界

诚实记录，不是遗漏：

1. **monitor / cls 两个 MCP server 返回模拟数据**，只有 Prometheus 告警查询是真的。
   接真实后端时替换 server，agent 侧不改。
2. **`chat.startStream` 的 thread 支持存疑**——文档和 SDK 示例互相矛盾，默认走 `chat.update`，
   streaming 在开关后面且带回退。要在真 workspace 里验。
3. **Socket Mode 的运维特性**：Slack 每几小时回收一次连接（约 10 秒预告），单 app 上限 10 条
   并发连接。建议跑 ≥2 副本，靠 §5.6 的幂等让重复投递无害。
4. **顶层 @ 的告警提议**尚未实现，当前顶层 @ 一律走对话。
5. **Slack 侧的写回和打分**（Block Kit 按钮）尚未实现。

## 设计原则

1. **事实归代码，判断归模型。** Slack 已经知道 root 消息是谁发的，再问模型一遍严格更差。
   一个决定如果能从元数据得出，就不要交给可能看错的东西。
2. **按来源路由，不按文本路由。** "这是哪条告警"是可以静默判错的语义问题；"这条 thread
   挂在谁发的消息下面"是查不错的元数据。决定要不要干活的闸门，用失败方式响的那个问题。
3. **让错误的做法不可表达，而不是禁止它。** 提示词里写"重规划不要增加步骤"是请求；
   `new_steps[:len(plan)]` 是保证。
4. **判错要么不可能，要么可见。** 不可能是最好的；做不到的时候，就必须让人一眼看出来、
   一句话能纠正。静默的判错才是贵的那种。
5. **窄问题不该缩小取证范围。** 提问的人往往正在猜，顺着他的猜测缩小搜索，正好错过原因。
6. **入口统一不等于执行统一。** Slack 没有导航栏，所以入口必须合并；但一个知识问题不该
   为此付出四次模型调用。
7. **降级要说出来。** 模型不可用、数据是模拟的、这次没有排查——每一个都要写在回复里。
   一份看起来完整但其实不完整的回复，是事故工具能产出的最危险的东西。
8. **import 不做 I/O。** 一个模块被 import 不代表它会被用到。
